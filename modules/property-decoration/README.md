# 装修管理后端

`property-decoration-manager` 拥有装修申请、配置、附件回执、办理轨迹、巡检验收任务和收退款核验记录；`property-decoration-service` 独立装配。只依赖 `property-base-core` 的公开只读命令读取项目、有效员工和客户房屋关系，不依赖其他系统 manager、不跨业务库查询基础表。

运行前先启动公共基础档案、SaaS 网关和认证基础设施。装修服务默认 HTTP 8505、集群 18505、RPC 28505；数据库 `property_decoration`。部署前核对目标环境端口、网关服务路由、命名空间和应用菜单。环境变量见服务 application.yml；密码、令牌和密钥只写入被忽略的本机配置或目标环境密钥管理。

装修基础配置不再接收或返回配置名称，手动保存和 Excel 导入均按既有匹配维度定位配置，不要求名称或生成占位名称。历史数据库名称列无需物理删除，应用不再映射和使用；配置主键、版本及历史申请快照不变。

配置匹配失败提示应说明配置属于当前装修应用，并引导管理员到本应用的“装修基础配置”核对项目、房屋类型、装修类型及办理场景，补充或启用相应配置；其他装修应用的配置不自动共用。 项目章、员工身份、客户房屋关系及任务角色的阻塞提示应指向对应维护入口；基础档案、文件及认证目录不可用时提示联系服务维护人员检查接入，不将服务故障引导为反复重试或重复创建角色。

目录调用会检查目标基础节点支持的具体命令。仅有 RPC 代理、但节点未安装客户房屋等命令时返回 503，不把未接通能力展示成空房屋列表；命令已安装且确无有权数据时仍返回正常空结果。

验收人员资格通过现有 `authService` 的 `GetAuthenticationCommand` 读取候选人的认证，沿用 `decoration.directory.role-server-id` 选择公共认证节点；命令保留指派人的上下文，由提供方检查候选 user 资产读权限。首验、二验候选只包含当前应用成员中的有效、启用员工；沿用巡更现有 `authService:user` 命令，在认证服务按启用账号、当前应用 `in-dimension$business_application` 成员关系及调用者 user 资产权限取得成员 ID，再经基础员工命令核实员工身份。不额外按指派人的组织归属筛选，也不把应用成员维度条件发给基础数据库；不额外要求候选人具有任务办理按钮权限。目标项目 read 范围通过基础组织树公开命令，在候选人的认证与应用 Scope 下求值，不在装修库重建组织成员关系。切换仅限该次只读命令，并清除继承的指派人显式 holder；原调用者上下文不变。不使用指派人身份替代、不依赖集群散列选取节点后的故障认证缓存；缺命令明确 503，拒绝或无有效候选仍拒绝指派。`POST /decoration/directory/employees/_query?projectId=...` 必须携带目标项目，先按候选人的项目资格过滤再分页；应用内匹配员工超过1000人时要求缩小姓名搜索，不截断伪造总数。提交指派实时复核应用成员、有效员工和项目权限三项资格，实际反馈接口保留原有按钮权限及任务本人校验。

检查配置Excel格式沿用原PC的19列：验收场景、所属项目、房屋类型、装修类型、检查大类及排序、检查小项、填报类型、必填/启用、小项排序、文本/数值/图片标准、上下限、选项、默认标准项和示例图片。项目名必须唯一映射到当前有权项目；房屋类型的编码或文案必须唯一映射到公共启用字典，不能从上传文件或浏览器声明主数据。公共字典只读契约为 `QueryPropertyDictionaryItemsCommand` / `propertyService:dictionary`，由基础档案持有，沿用公共字典的认证读取规则，仅返回启用分类的启用项；缺少命令时消费方503，不猜测编码。

导入按项目、房屋类型、装修类型、场景分组，同分类同名小项合并并保留ID，未出现项保留。`CheckItem.categorySort` 表示分类排序，`sort` 表示分类内排序；已有未设置分类排序的配置沿用整体排序。文件解析与合并计划不执行写入或上传，任一行无效时不产生可执行分组。模板和数据都使用同一19列；物理行号用于错误定位。支持xlsx浮动图片及WPS DISPIMG图片，仅解析本工作簿内资源，不执行普通公式或读取外部图片。最大10MB/1000个数据行/64MB展开内容；每行最多一张JPG或PNG、2MB。POI解析由编排层调度到boundedElastic。

检查导入端点为 `GET /decoration/configurations/checks/import-template`、`POST /decoration/configurations/checks/import?requestId=...`（multipart `file`）和只读 `GET /decoration/configurations/checks/import-result/{requestId}`，均使用配置保存权限并要求有效员工。请求号最多64字符，按应用、租户和操作者隔离；同键不同文件拒绝。先捕获所有现有配置版本、完成整批合并预检，再上传私有模板图片，配置与 `pd_configuration_import` 成功收据同事务保存。版本冲突或任一保存失败整批回滚，已知临时图片在事务结束后补偿删除；不能确认外部上传结果时不自动重试。外部上传/写库开始后的有限操作不随浏览器断线取消，客户端可凭原请求号查询结果。同请求竞争先回滚失败事务，再核对赢家收据，防止重复增加配置版本。结果读取重验当前项目权限，不重新执行导入。成功收据不保留原始工作簿。

```sh
mvn -pl :property-decoration-service -am verify
```

使用 Java 17，行为测试通过 Testcontainers 创建隔离 PostgreSQL，不读写业务库。发布产物为 `services/property-decoration-service/target/application.jar`，只包含本系统 manager 和公共 core；本地 application-local.yml 不打入产物。

业务接口仅提供受控动作，不开放通用实体保存或物理删除。项目范围来自基础组织树命令的 AssetsHolder 授权结果，只接受显式标注为项目的节点；平台直属应用允许无技术租户，仍须具备平台激活的应用 Scope。`decoration.directory.server-id` 可将基础命令固定到指定公共节点（默认使用集群选择）；装修 SQL 再固定可信应用与租户边界。分页、详情、附件、统计、导出及动作使用同一边界。创建通过唯一房屋占用与稳定请求键防并发；动作通过聚合行锁、版本与轨迹原子提交。超时核对端点只读查询；同键不同内容拒绝。

附件内容通过 SDK 已有 `fileService` 流式上传、下载和删除命令访问公共文件服务；通过平台 `CommandServices.getReactive(fileService)` 发现实际提供方，与巡更保持一致，不再使用 `decoration.files.server-id` 固定节点。独立启动关闭 `file.manager.command.enabled`，避免本机默认文件实现优先于集群公共提供方。服务不可用或命令缺失时拒绝操作，不退回本机文件存储。装修库仅保存私有业务回执和公共文件 ID，浏览器读取仍经过装修项目、应用和租户范围校验，不暴露通用文件访问地址。上传或补偿删除均不自动重试，避免未知结果时重复写入。 文件ID属于既有公共HTTP存储、集群文件提供方无法解析该ID时，可显式配置 `decoration.files.gateway-url` 和可选 `gateway-service-id`，通过既有 `/file/{id}` 接口读取，上传同步使用该入口的 `/file/upload`，避免跨节点存储不一致；上传不设置公开访问选项。仅转发当前请求的登录令牌、应用范围及租户域，网关地址和服务选择来自服务端配置，不接受客户端URL或路由头。不记录凭据、不开放通用代理，未携带当前认证时拒绝读取。

独立服务关闭原始 `file.manager.upload-filter` 自动注册，改为装饰同一公共过滤器：保留公共后缀策略，并恢复其 multipart 请求重建后请求头的大小写无关读取。此适配不从客户端推断租户，也不替代平台租户检测和认证。

验收申请使用 `AcceptanceRequest`，必须提供申请验收日期；提交时间、申请人和来源由聚合事务从可信上下文生成。人员指派仅使用 `Acceptance`，不得修改已提交的日期或申请人。任务保留创建时的装修和本轮验收申请快照，后续轮次不覆盖历史；旧任务未记录字段返回空值，不根据任务创建时间推算申请日期。
PC 首验、二验各使用一个列表合并验收办理与记录，显示已具备前置条件的待发起装修及实际发起过的验收。待发起记录没有申请日期、人员和轮次，不创建虚构任务；发起、失败重提、指派和查看详情均在行内进入。同一装修的首次、二次验收各汇总一行，失败后重新发起仍更新该行，人员任务与每轮反馈完整保留在详情和操作轨迹。业主首次申请和失败后重提均进入待指派，由物业使用员工权限核验并指派本轮验收人，不在业主请求中自动沿用旧验收人或读取员工目录。记录查询为 `POST /decoration/tasks/acceptance/{kind}/_query`（`kind=firstAcceptance|secondAcceptance`），`includeEligible=true` 在数据库分页前同时纳入满足当前备案/首验门槛的装修；默认 false 保持仅查询已申请记录的原契约。`requestAllowed` 仅表示PC来源及业务资格，按钮权限和提交资格仍独立校验。先汇总最新轮次再按 QueryParam 筛选、分页，沿用装修任务查询权限及申请的应用、租户和授权项目范围；待指派也计入记录，多人未全部反馈时维持待验收。列表不返回附件及任务正文。该汇总使用现有 PostgreSQL 业务库聚合函数；跨数据库迁移时需替换姓名聚合。个人任务与详情任务接口继续逐人、逐轮次返回。
PC 各装修业务列表的“装修状态”固定在右侧、操作列之前。巡检任务、违规记录、自检表及验收记录使用 `decorationStatus` 展示申请的当前状态，记录自身的 `status` 仍表示办理/自检结果；前者只读、不写入历史快照。任务与自检列表仅在分页后批量读取授权申请的 ID、状态，不逐条加载详情；验收汇总直接投影申请当前状态。



整改任务的 `feedback` 仅表示原巡查意见。提交整改、整改复核、重指派及重发分别在 `details.handlingRecords` 追加办理人、时间、处理后状态、意见与当时复核角色；提交整改另存当次附件。快照与任务状态在申请聚合事务中提交，幂等重试不重复记录，后续整改不得覆盖此前附件或意见。重发创建新任务并保留原巡查内容，通过 `sourceTaskId` 关联原记录。沿用聚合动作和HTTP/SQL追踪，无新增常驻状态或MBean。

`DecorationFinanceGateway` 与 `DecorationNotificationGateway` 是真实集成边界。无提供方时，资金办理和通知发送返回503；不能在客户端或数据库中手工制造支付成功以绕过发证门槛。财务核验校验资金方向、单据类型、金额、归属与唯一回执。二验后一次性退费结算成功（`refundStatus=2`）才代表装修办理结束，PC与小程序使用同一结束标志。禁止手动结束或登记结束时间绕过退费。外部调用必须支持契约中的稳定幂等键。

退款仅在二次验收通过后一次性结算。金额取申请冻结协议的 `refundAmount`，未配置时退还实收保证金；配置不得为负、超过保证金或超过两位小数。旧协议的 `firstRefund`、`secondRefund` 只合并为总额，不再开放首验退款；历史已核验退款从总额扣除，不能重复退。零金额仍需显式结算，不伪造外部交易回执。退款成功才释放房屋占用并自动结束，PC/H5使用同一资格规则。

本机联调可显式设置 `decoration.integrations.simulated.enabled=true`（环境变量 `DECORATION_INTEGRATIONS_SIMULATED_ENABLED=true`）启用模拟支付、退款及消息提供方，默认关闭。PC/H5 显示“模拟缴费”“模拟退款”按钮，调用管理端或本人端 `/{id}/simulation/payment`、`/{id}/simulation/refund`，由服务端生成模拟单据。独立测试接口仅接受模拟提供方，关闭模拟或配置真实提供方时返回503；复用原缴费/退款动作权限、本人关系、状态机、金额核验及动作幂等，不要求测试者手工编造财务单号。真实线下核验接口仍要求物业员工及真实单据。模拟回执持久化于装修库的 `pd_simulation_receipt`，同请求重试返回原结果，同键不同内容拒绝。回执提供方标记为 `SIMULATED_DECORATION`，能力接口返回 `simulated=true`，PC/H5 详情展示模拟提示；不产生真实资金交易或消息发送。该配置仅用于明确授权的测试实例，不代表真实财务接入完成。

同一模拟开关也启用 `SimulatedDecorationChargeItemGateway`，为原收费科目选择接口提供“装修保证金”和“装修服务费”，支持名称包含搜索及分页，不创建或修改收费主档。正式收费目录提供方存在时优先使用正式提供方；关闭模拟开关且没有正式提供方时，仍明确返回503。项目、员工及应用权限继续由原目录入口校验，不提供假角色或绕过授权。

备案状态独立于装修流程状态：当前版本未打印或下载为待办理；打印或下载后先判断有效期，再判断延期快照，否则为已完成备案。已发布的旧数据仅有打印时间时保留原流程资格，但不补造领取人、领取时间或图片。`permit` 列支持框架 `json_value` 查询打印时间，以及 `decoration-permit-state` 条件（`pending`、`issued`、`extended`、`expired`，值可多选，`$not`取反）。状态以服务端查询时刻计算，条件在现有权限边界内执行后分页，不加载全量记录。此映射复用独立服务已限定的 PostgreSQL 框架JSON支持，不修改现存文本快照类型；其他数据库需提供对应JSON映射。查询沿用框架HTTP/SQL观测，无常驻状态，不新增手动追踪或MBean。

备案证件通过 `GET /decoration/applications/{id}/permit/document` 只读准备，要求打印权限、有效员工、统一申请范围及已审核收款；响应 `Cache-Control: private, no-store`。`DecorationProjectSealGateway` 为项目章只读集成边界，实现必须保留认证/资产/租户上下文，经公共档案及文件公开能力获取章，不接受客户端URL或装修附件替代。缺提供方503、项目未配章409；校验应用/租户/项目归属、PNG/JPEG真实解码、2MB和4096×4096上限，图片与摘要运算在boundedElastic。首次准备返回申请快照、私有data URL和SHA-256摘要；当前有效期已有打印图片时返回原私有附件回执，不再读取最新项目章。不在装修复制印章主档，不臆造公共命令或默认章。

PC先生成完整带章PNG，通过装修私有附件 `purpose=permit` 上传（打印权限、有效员工、本申请范围、20MB、真实PNG解码及4096×4096限制），再以原版本、稳定请求号、`PrintPermit.sealDigest` 和 `snapshotFileId` 调用 `/{id}/permit/print`。聚合事务校验章摘要及专用附件归属；缺章、换章、无效图片及未付款不留下打印登记。每次打印或下载追加输出类型、图片回执、有效期、操作人和时间，详情展示原图；重复打印与下载复用已冻结的原图，不重新套用新章或新模板。独立证件保留原施工时段、13项须知及版式，业主姓名、联系电话沿用申请冻结信息，不另设备案人字段。未知结果先只读核对原请求，成功后输出同一图片；设备失败可重试输出而不再次登记。`PrintPermit.outputType` 接受 `print`（旧请求默认值）或 `download`，分别更新 `printTime` 或 `downloadTime`，沿用打印权限；操作轨迹分别记录 `printPermit`、`downloadPermit`。首次输出自动完成当前版本备案，不要求登记领取；重复输出不能倒退验收状态。记录只证明发起输出，不能证明纸张输出、文件落盘或领取，浏览器取消输出不回滚归档。

历史 `POST /decoration/applications/{id}/permit/collect` 契约保留兼容旧客户端，新增页面不再提供该动作，流程资格不再依赖领取。既有领取快照只读保留，不补造领取人或领取时间。延期清除当前版本的 `printTime` 和 `downloadTime`，保留旧版图片与操作历史，输出新版证件后完成当前版本备案。备案筛选、概况指标、巡检及验收统一使用当前版打印或下载完成口径，并兼容既有领取记录。

领取后延期追加原有延期记录，保留旧版图片、打印及领取记录，清除当前打印/领取摘要并进入待领证状态；新有效期必须重新生成、打印和登记领取。未保留图片的旧打印时间在延期时转存 `legacyPrintTime`，不伪造历史图片或操作人。现有聚合/HTTP/SQL追踪覆盖这些动作，临时图片有限生命周期，无新增常驻任务或MBean。

PC/H5 源码和业务对照文档位于相邻装修管理前端仓库。此目录不包含生产凭据或自动部署指令。

PC在线审核使用 `POST /decoration/applications/_query?view=review`，只查询列表标量字段及服务端汇总的 `materialReview`、`drawingReview`，不选择或返回完整 `details`、`permit`、`inspectionPlan`。审核状态沿用自检归入资料、驳回优先、空选填项不占待审的口径；分页、筛选、应用/租户/项目范围与原申请查询一致。打开详情后再请求 `GET /decoration/applications/{id}`；原查询、H5和导出契约保留。

新增申请区分办理来源：PC服务台要求上传业主线下填写签字的自检文件，保存于 `details.selfInspectionFiles`，不提交在线签署文书或结构化答案。业主H5自检沿用原系统九项：电话线、闭路线、宽带线路、可视分机、门磁、其他、厨房排水、主卫排水、生活阳台排水，提交 `selfInspectionItems[{key,value}]`；键不可缺失、重复或替换，汇总结果由服务端计算。H5签署 `selfInspection` 完整自检图片，正文绑定权威房屋、业主、电话和九项答案，不依赖施工信息。H5每份已上传的启用装修资料还必须具有 `material:<itemId>` 签署，正文绑定申请信息与配置模板回执，资料文件必须等于对应完整签字图片；图纸独立上传，不要求签字。PC资料按启用配置上传线下签字文件，无固定四文书要求。两端必填资料/图纸校验、私有回执归属、资产范围和附件消费仍在原创建事务内，无新表或权限。历史正文、说明和附件只读保留，不回填重画，新表单需前后端配套更新。

自检与签署契约由 `DecorationSelfInspectionForm`、`DecorationDocuments` 和申请创建事务共同约束，相关7项规则及持久化测试通过，装修独立服务打包通过。在线资料签署正文按配置项及模板冻结，PC导入与H5在线签署不得混用。

装前自检使用独立 `pd_self_inspection` 记录。与旧系统一致，业主申请创建时在同一事务生成一份自检快照，PC 不单独新增；请求重试不重复生成。PC `/decoration/self-inspections` 提供分页、详情和带版本的逻辑删除，沿用 `decoration-application` 的查询/删除权限及统一项目、应用、租户范围。删除仅隐藏自检记录，不改装修申请、办理轨迹或附件归属；附件回执仍绑定原申请，不用自检 ID 冒充装修 ID。现有申请历史不自动回填为自检记录。验证覆盖业主创建/重试/回滚、PC 不生成、跨范围拒绝、分页筛选、删除后快照与附件保留。新增接口沿用框架HTTP/SQL观测，创建沿用聚合追踪；无常驻状态，不新增MBean。

概况工作台使用 `POST /decoration/applications/_dashboard`，返回统计时刻 `asOf`、`metrics[{key,group,value}]` 及近12个月的 `trend[{month,created,ended}]`。趋势以北京时间自然月分别聚合创建时间、退费完成申请的实际结束时间，半开区间且缺月补零，前端可切换近6个月／近一年；与摘要在同一授权SQL中计算。顶部显示累计装修房屋（项目+房屋去重，最新申请承接明细）、当前在装、本月新增申请、本月退费完成装修；月份采用上海自然月。在装要求已领证、已开工、首验未通过且尚未结束，不以退款状态推断施工状态。统一在线审核只计一次，另列驳回待补资料。物业待办、业主待办、备案到期和延期待换领均按涉及申请数去重，同一申请可出现在不同指标中。新打印不等于领取；延期后按当前版本领取状态判断。单条聚合 SQL 复用 DecorationScope，任务关联同时校验应用、租户、项目和装修ID。

指标明细使用原 `POST /decoration/applications/_query`，追加 `id` 条件 `termType: decoration-overview-metric`，值为 `{metric,asOf}`；固定指标表达式、绑定日期参数、框架分页和原有权限边界保持一致，不全量加载申请详情。旧 `_statistics` 报告继续保留兼容已发布前端，其旧流程分布、退款划分和环比口径不再用于新版概况。

管理端记录修改区分计划竣工与实际结束：`/{id}/completion-time` 仅修改未结束申请的计划日期；`/{id}/actual-end-time` 在 `save` 权限下仅允许对退费已完成的申请纠正实际结束时间，要求不早于申请开始；不得提前结束、改变状态或释放同房占用。`/{id}/end` 保留既有动作地址，仅允许为退费已完成的申请补充结束说明。结束状态与房屋占用只由退费成功事务写入，不支持清空时间重新激活，不改计划日期和财务状态/单据。后者复用统一范围、有效员工、事务、版本、幂等及历史快照。PC详情在结束后保留时间纠正入口，业主接口不开放该动作。记录页“是否生效中”沿用旧许可区间开区间口径，与装修是否结束独立；备案页不再把发证员工当作业主或备案申报人展示，姓名和电话统一沿用申请快照；历史员工电话字段保留只读兼容。

日常巡检通过公开`authService:role`命令读取当前应用可见的启用角色；`decoration.directory.role-server-id`可明确指定节点。缺命令返回503，合法空目录正常返回空页。模板应允许role资产的business_application选择策略，应用绑定可用角色，办理角色配置同策略。候选读取不代替本人执行资格，复核角色名称由服务端验证后冻结，重指派同样校验目录。

巡检计划冻结各角色的间隔天数（1～1000）、有效时段、检查项、整改复核角色及指派人。按上海自然日与计划起始日的间隔计算，当天到期角色共享一项日期任务；各角色周期分别生效，前期未完成不阻断后期。一项任务仅反馈一次，办理者须为当前有效员工、有目标项目和handle权限且当前认证角色匹配。重新指派不覆盖当天已生成的快照。PC巡查页先列已发证装修申请供指派，日期任务位于独立页签。

计划与索引游标位于申请聚合，后台响应式每分钟处理最多100份计划、每份最多追赶30个自然日。首次指派不补造过去任务，停机恢复按持久化游标补齐；结束/删除停止生成。后台与人工动作共用申请行锁，日期任务使用申请+日期的确定性ID，多实例/重试不重复；游标更新不增加人工动作版本，失败整份事务回滚。decoration.inspection.scheduler.enabled可关闭调度，delay和initial-delay设置毫秒间隔。批级追踪/property/decoration/inspection-generate复用平台SQL观测；JMX org.jetlinks:type=DecorationInspection,name=Generator提供累计生成、失败和最近成功时间，无业务修改入口或隐私字段。

员工H5通过 `POST /decoration/tasks/mine/_query` 查询个人任务：验收按可信本人指派，待巡检按当前认证角色，待整改复核按冻结复核角色，历史按实际执行人或办理记录中的操作者。统一应用、租户和有权项目条件与个人条件以AND组合，JSON角色/办理快照在PostgreSQL中筛选后分页；不接受浏览器指定操作者。接口要求有效员工及任务查询权限，办理仍分别检查handle/review权限和任务本人/角色资格。

个人任务、管理端任务列表及申请详情任务查询均返回当前读取人的 `feedbackAllowed`、`reviewAllowed`：分别表示待办任务的执行人/巡检角色资格与待复核任务的复核角色资格。字段只在读取时计算，不存入任务快照；PC、H5 将其与已有菜单动作权限取交集后展示办理入口。字段不授予权限，提交时仍完整校验员工身份、项目范围、任务状态及本人/角色资格。

巡检不通过在同一聚合事务生成 `owner_rectification` 记录，业主可直接读取并提交整改，不再经过整改通知审批；巡检计划只要求巡检角色与整改复核角色。业主提交后进入 `waiting_review`，通过/驳回及办理历史仍按既有角色复核规则执行。外部通知仍需提供方真实受理，不以直接下发业务任务伪装推送成功。既有历史快照中的通知审核字段只作历史信息保留，不再产生新审核动作。

施工人员通过 `POST /decoration/applications/{id}/permit/workers` 独立登记，沿用 `permit` 操作权限及聚合员工/范围/版本/幂等边界，必须已审核且已缴费；保存登记不生成证件。登记内容保存在申请详情，包含操作者和时间。生成备案优先采用已保存登记；已发布的原备案接口仍允许在一次请求中提交登记并发证。发证后继续登记只维护人员名单，不覆盖证件安全负责人、施工内容、打印图片和领取信息。人员日期必须有效且截止不早于进场，最多200人。延期沿用原流程，仅在到期前七天内或过期后办理，保留旧证历史并重新打印或下载。新接口沿用HTTP与聚合持久化观测，无新增后台状态或MBean。

## 业主房屋入口

业主登录后从本人有效关联的全部有权房屋进入，依次选择房屋、装修申请、办理步骤。`GET /decoration/mobile/applications/_houses` 先以 `QueryCurrentPropertyHousesCommand` 一次读取本人房屋候选，再仅对候选涉及的有权项目调用公共房屋关系命令 `mine=true`，取项目、空间资产与本人关系交集，不遍历无关项目；同项目同空间去重。同一请求复用已核验项目范围查询装修汇总，不重复读取组织树。返回每房屋在当前应用中的本人申请数，以及与创建申请唯一锁一致的房屋占用标志。占用只读取公共档案已核验的本人房屋在当前租户下的activeHouseKey，不因申请登记在其他业主账号或装修应用而漏计；只返回布尔值，不扩大申请记录、详情和附件权限，不包含申请文书、附件或图纸。`POST /decoration/mobile/applications/_summaries` 分页返回本人申请的轻量列表，继承应用、租户、项目及本人范围；选择申请后读取既有详情接口。房屋首页的装修房屋、办理中房屋按套计数，不把同房多次申请计作多套。公共目录故障明确报错，不返回部分房屋或伪造空列表。

## 流程提醒与通知

装修步骤完成后的下一步提示由PC/H5共用流程规则派生，全部资料及保证金通过后才提示缴费。真实状态转移与办理轨迹在同一事务写入 `pd_notification`：申请提交/驳回、全部审核通过、缴费完成、备案完成/延期、首验和二验申请/指派/结果、退款成功。轨迹ID同时作为通知ID，幂等重试不重复入队，业务回滚不产生通知；不回填历史轨迹。流程提醒收件人取申请业主账号；任务通知另按可信指派及复核角色展开，不开放任意收件人或批量广播。

`POST /decoration/mobile/applications/_notifications/_query` 沿用业主query权限，叠加本人、可信应用/租户及基础档案已授权项目范围，只返回通知展示字段。点击链接仍由本人详情接口核验资格；通知不授予申请访问权限。链接只带应用、装修ID和步骤，不携带凭据、手机号或附件地址。

后台复用 `notify-core` 的 `SendUserNotificationCommand`，固定 `inside-mail` 通道及 `property-decoration` 通知源；不修改公共服务。默认每5秒读取最多50条已提交记录，CAS租约避免并发发送，20秒命令超时及有上限退避重试；失败不回滚业务，不把入队显示为外部送达。公共命令没有幂等收据，成功应答丢失时属于至少一次投递。`decoration.notifications.enabled=false` 可关闭站内投递，装修自有通知查询仍可使用。JMX `org.jetlinks:type=DecorationNotification,name=Delivery` 提供发送、失败与本轮候选数量；批次span `/property/decoration/notifications` 不记录隐私载荷。微信订阅消息和APP系统通知需现有通道另行接入，不用站内信代替其送达状态。


### H5身份与员工通知

`GET /decoration/mobile/identity` 在当前可信应用 Scope 下返回 `{owner,staff}`；分别要求 `decoration-owner:query` 加有效本人房屋、`decoration-task:query` 加有效员工档案。无员工档案仅关闭员工身份，公共目录故障仍传播。双身份选择与切换属于装修 H5，不改变认证、应用成员或租户授权。

员工通知通过 `POST /decoration/tasks/mine/notifications/_query`，要求现有任务查询权限、有效员工、本人与应用/租户/项目范围；角色通知还检查当前角色。新通知记录区分 `recipientSide`、`taskId/taskVersion`、`roleId` 及可信 `dispatcherId`，历史空端别兼容为业主。角色意向不展示为个人通知。

首验/二验指派同事务入队 `firstTaskAssigned/secondTaskAssigned`；巡检不通过或重发整改入队业主 `rectificationRequired`；业主提交或重提整改入队 `rectificationReview`；复核通过/驳回入队业主 `rectificationPassed/rectificationRejected`。复用既有整改状态机和按钮，不创建第二套复核记录。通知失败不回滚业务。

后台以原计划指派人的实时认证和应用资产范围查询启用角色成员，再逐人核验实时应用成员、任务动作权限、有效员工、项目权限和复核角色。Scope本身不作为成员授权证明。不伪造系统管理员、不持久化token、不以业主权限枚举员工。角色事件按人生成稳定通知ID，每人独立重试，角色展开不计为已送达；任务版本、状态、指派人或复核角色变化使旧员工待办取消。角色已移除、员工失效或应用成员撤销不继续投递；目录暂时不可用保留重试。

公共 `SendUserNotificationCommand` 仍使用 `inside-mail`，detail 保留 `applicationId/decorationId/step/url`，增加 `side` 及可选 `taskId`。业主整改为 `step=rectification`；员工任务为 `step=task`。APP宿主应将定位字段转换到装修模块路由，业务详情仍重新鉴权。系统推送及真机送达另由APP通道接入，不能用站内入队/发送状态代替。
