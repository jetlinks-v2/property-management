# 品质核查菜单与模板

本目录的 `menus.json` 和 `template-grant.json` 只提供品质业务菜单及授权树；公共组织、用户、空间、客户和字典由 `property-base-ui` 唯一提供，不在品质模板中复制。后端为独立 `property-quality-service`，基础档案由 `property-base-service` 维护。

先按 [公共基础管理接入](../property-base/README.md) 初始化公共菜单一次，再导入品质业务定义、配置应用模板及服务套餐、刷新目标项目订阅快照，并为角色配置业务与所需公共菜单授权。所有操作均合并现有配置，保留原资产范围；定义存在不等于模板、订阅和角色已授权。

已有 `quality-system-*` 节点需按公共对应表迁移，验收后停用；前端源码移除旧页面不会自动修改持久化菜单。项目、员工和分配候选继续使用 `/quality/context/**` 的业务过滤，不能用公共人员列表替代执行资格。PC 构建必须同时包含 `quality-inspection-ui`、`property-base-ui` 及实际 SaaS 宿主模块，独立员工 H5 沿用自己的构建与接口。

## 两级业务导航

品质应用使用 Cloud 应用壳层的左侧一级导航与内容区顶部二级导航。项目授权树以 `quality-inspection` 为系统根，独立应用通过前端 `getMenuFilters` 只展开该根的一层已授权子项。应用一级分为品质首页、公司基础配置、公司核查、项目基础配置、项目核查、应用管理；基础配置组包含配置和模板，公司组另含评分评价，核查组包含任务、记录和报表，应用管理包含设置与导出。各叶子菜单保留原 ID、URL、按钮及资产策略，父目录仅组织导航，不授予业务动作。不同业务使用对应图标。

已有环境需增量更新菜单的 parentId、图标、排序和翻译，补齐模板、套餐和已有角色中实际授权子项的父目录及系统授权根；保留原动作与资产范围。菜单层级既存在于全局定义也存在于授权快照，不能只改前端 JSON 或全量覆盖角色。迁移公共基础管理时仅为原有职责映射授权，不给核查、整改或只读员工增加基础维护权限。完成后检查应用实际菜单树、一级选中、内容区二级切换、直接访问及刷新。

## 授权快照转换

`migrate-menu-grants.py` 可离线转换导出的模板、套餐或角色授权。`--current` 指向授权快照，`--definitions` 提供原 `quality-system-*` 及公共 `charging-*` 菜单的完整定义（可用逐菜单详情 API 导出），`--output` 写入待审核结果；转换不请求服务器。Cloud 授权快照可能省略 `permissions`，脚本按原定义解析已授权按钮，保留动作和资产范围；缺失原定义时失败，避免静默撤掉管理员权限。修复中途转换时，可显式用 `--baseline` 指向迁移前备份。

完成转换后，将结果逐一合并到原模板、套餐和角色，并刷新目标项目的订阅快照；通过实际账号检查公共用户的标注/同步权限，以及普通员工无法维护公共档案。`python3 deploy/quality/migrate-menu-grants-test.py` 覆盖省略权限定义、禁止扩权、幂等和恢复。

大租户候选人通过有限并发解析实时授权，初次核查分配与整改/转派均保留原应用、动作和资产校验；不缓存授权快照，也不按人员组织粗筛替代资格校验。

## 项目绑定迁移

公司检查内容配置及模板使用基础档案项目 ID，独立的 `business-type` 维护已停用。公司共用条线、科目、检查要求不绑定项目；项目级基础配置仍在项目内维护。配置与模板归属保存后不可变；需要用于另一项目时，复制为新配置/模板并重新选择该项目检查项。

更新前通过授权接口导出 `applicationId`、`tenantId`、`projects`、`configurations`、`tasks` 到一个 JSON 快照：项目取 `/quality/context/projects`；配置和任务查询取消分页、限定当前应用，遍历完整结果。快照与映射文件放在权限为 600 的部署备份目录。映射示例：`{"businessTypes":{"旧业态配置ID":"基础项目ID"},"configurations":{"特定模板或检查配置ID":"基础项目ID"}}`。映射必须由真实项目核对，不能把旧配置 ID 当项目 ID。

运行 `python3 deploy/quality/migrate-project-bindings.py --snapshot snapshot.json --mapping mapping.json --output migration`，检查 `plan.json` 后再执行 `apply.sql`。脚本只生成 SQL，不连接数据库；应用 SQL 使用租户、应用和版本条件，任何并发修改都会使整批回滚。备份品质数据库后，暂停品质写入并在 PostgreSQL 执行 SQL，再发布后端及 PC/H5。其他业务服务无需更新。

模板、检查配置、历史任务的项目不一致时脚本拒绝生成迁移，须先按真实项目拆分复用模板和检查配置并核对历史关联，禁止猜测或覆盖。工单、检查记录、照片、分数、整改复验轨迹不在迁移写入范围。`rollback.sql` 仅在迁移后对应配置尚未再次修改时可用；已有新写入时需按备份和版本逐项处理。
