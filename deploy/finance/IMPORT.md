# 收费 Excel 导入部署与使用

本说明适用于历史应收、实收、预收、押金、临时收款。导入和审批均固定在页面已经选择的项目内，不跨项目匹配资料。

## 部署

1. 备份收费数据库，停止 `property-finance-service`。
2. 已有数据库执行 `modules/property-finance/sql/migrate-collection-import.sql`。PostgreSQL 脚本可重复执行，只创建收款导入批次、暂存明细及索引，不更改原有应收、实收或余额。使用非 `public` schema 时先替换 schema。
3. 若旧版本尚未部署历史应收审核，先按原升级说明执行 `modules/property-finance/sql/migrate-historical-import-review.sql`；已经执行的不需要重置历史数据。
4. 启动基础服务与新版收费服务，部署收费前端模块。
5. 重新初始化收费模块菜单，并给需要操作的角色分配各页的导入、导入记录、审核通过、驳回、编辑待审明细权限。历史应收的待审编辑沿用应收“审核”权限；收款导入使用 `property-finance-collection-import` 资源的 `import/imports/approve/reject/import-edit` 动作。

示例执行方式（连接参数由部署者按环境提供，不把密码写入脚本）：

```powershell
psql -h <数据库地址> -p <端口> -U <用户名> -d <收费数据库> -v ON_ERROR_STOP=1 -f modules/property-finance/sql/migrate-collection-import.sql
```

新部署使用 EasyORM 创建实体表。不能把新库的建表成功等同于已有库完成升级。

## 操作顺序

1. 选择项目，进入对应的历史应收导入或收款导入窗口。
2. 从后端下载该项目模板。红色表头必填；第一张表填写业务数据；“填写示例”页只有一条脱敏示例，不参与导入。项目参考页及下拉提供真实匹配范围。
3. 历史应收先填完整房屋路径、有效客户、项目科目和标准、计费起止、应收账期、应收日期、原应收、减免与实际应收。合同编号、备注选填，原应收减减免必须等于实际应收。
4. 实收通过模板“应收参考”中的应收明细标识匹配已审核应收，填写原收款单号、收款公司、支付方式、收款金额、收款时间及缴款人；需要减免时填写减免金额和原因。收款金额必须符合所选应收当前可收金额。
5. 预收、押金、临时收款通过房屋完整路径、客户名称及收费科目/标准匹配当前项目，填写收款公司、支付方式、金额、收款时间、缴款人。预收和临时收款还需填写计费起止，临时收款填写账期。押金可按收费科目存入，其他条件必填以模板说明及当前收费标准为准。
6. 上传 Excel。系统先读完并校验整个文件，所有行通过后才事务暂存；此时不会生成正式账单、收款流水或改变资金余额。任一行失败整份文件不暂存，失败批次保留物理行号、字段和原因。
7. “导入记录”是只读记录列表；“导入审核”是审批工作台。工作台支持搜索、分页、批次审核和驳回、进入明细单行或多行审核，以及修改尚未审批的明细。
8. 待审修改重新执行字段、项目、房屋、客户、标准、金额、会计期间和资产权限校验。批次及明细版本必须匹配；已通过或已驳回明细不可编辑。
9. 审核通过才发布正式财务结果。实收复用收银台收款服务并更新对应应收已收和欠款；预收、押金复用资金存入服务；临时收款复用原临时收款服务。后续在各业务台账查询结果。

收款时间按 `yyyy-MM-dd HH:mm` 填写，界面显示到分钟，接口兼容 ISO 时间。非实收的数量为选填，填写时须为正数、最多 4 位小数及 12 位有效数字；仅临时收款的账期必填。实收减免金额为正数时减免原因必填，最多 1000 字。

收款审核后的交账状态从“已收未交账”开始，继续使用交账明细、交账审核流程。导入原收款单号用于追溯和防重，不伪造已经完成的交账、入账记录。导入审核人是本次实际操作人，收款时间保留所填历史时间。

## 失败与并发处理

- 支持 `.xlsx/.xls`，单文件最多 10 MiB、500 条业务数据；模板输出 `.xlsx`。不接受公式单元格，不截断超限数据。
- 第一张表按模板表头读取，错误使用 Excel 物理行号，包括中间空行。先修正失败原因，再重新上传完整文件。
- 同一项目、收款类型的原收款单号不能重复；同一实收文件不能重复收取同一应收。正式应收身份也在审核发布时检查，防止两个待审批次重复入账。
- 已成功暂存的原收款单号保留防重身份，包括最终被驳回的明细；发现资料有误应在待审时修改。校验失败的文件没有暂存明细，修正后可用原单号重传。
- 审核时重新验证当前资料、可收金额和会计期间；暂存后发生退款、收款、结账或资料变更时，可能需要修改待审资料后再审核。
- 同次多批次/多行决策使用一个事务，任一项失败全部回滚。收款批量审核每次最多 20 批；单批内可审核全部待审行，指定明细每次最多 100 行。
- 陈旧版本或重复审核返回冲突，不产生第二次收款；稳定的导入明细请求号继续由原财务服务保证幂等。
- 已关期的数据不能通过修改收款日期或计费日期绕过限制。所有接口同时验证按钮权限、项目和空间资产权限。

## 历史应收与计算任务

历史应收没有收费设置，不会被周期出账任务再次生成。导入时冻结原应收和收费规则快照，后续标准单价、面积或逾期规则变更不覆盖历史快照。

历史应收本金全期计提并标为已关期，计提、关期任务不重复改写本金；滞纳金任务仍处理未收历史根账。拆分后沿来源链只处理有效叶子账，不恢复原账欠款；已收清、财务月结及支付占用继续遵守原有约束。

调整、拆分继续通过各自按钮审批。调整累计到历史金额，重算使用导入快照；收款按实际剩余应收核销。持久任务身份包括账单、任务类型与业务日期，同日重跑不会重复累加费用。

旧系统审批与发布分两步，由后台发布任务逐行落账；此版本在按钮审核事务内直接发布，失败整次回滚，不需要另启“导入发布”定时任务。保留审批、重校验、幂等、任务重试及财务历史，避免“审批成功但尚未发布”的中间状态。

现有每日计费计划由 `property.finance.billing-job` 管理：生成 `00:00`、计提 `00:10`、逾期 `00:30`；关期默认关闭，启用时为 `00:20`。调度器每 30 秒检查到点任务，重启会补跑当天已到点计划。这与基础资料每小时同步相互独立。

## 接口范围

历史应收：`/property/finance/projects/{projectId}/receivables/imports`，待审修改为 `PUT /{recordId}/lines/{lineId}`；请求包含批次 `version`、明细 `lineVersion` 和模板对应业务字段，响应返回最新 `record/line`。

收款：`/property/finance/projects/{projectId}/collection-imports/{kind}`，`kind` 为 `RECEIVED/ADVANCE/DEPOSIT/TEMPORARY`：

| 方法 | 相对地址 | 用途 |
| --- | --- | --- |
| GET | `/template.xlsx` | 项目模板 |
| POST | 根地址，multipart `file` | 全文件校验并暂存 |
| POST | `/_query` | 批次记录分页 |
| POST | `/{recordId}/lines/_query` | 暂存明细分页 |
| PUT | `/{recordId}/lines/{lineId}` | 双版本编辑待审明细 |
| POST | `/{recordId}/_approve`、`/_reject` | 单批或指定明细审批 |
| POST | `/_approve`、`/_reject` | 多批次原子审批 |

单批决策 `{version,reason,items:[{id,version}]}`，`items` 为空表示该批全部待审行。多批决策 `{records:[{id,version}],reason}`。修改明细 `{version,lineVersion,payload}`。前端不能直接修改正式财务表或余额。
